Thank you for this, and apologies that it waited so long. With no cantillation specialist available to review, we checked it against the repository's own data and the standard references. The change looks right.

**What the current value means.** `n="2"` is the Oleh veYored level: 358 of the 362 Oleh veYored words in Psalms, Proverbs and the poetic part of Job carry it. Every verse in those books that begins with a plain Azla Legarmeh and has no Oleh veYored is coded `2`, all 22 of them. That looks like a blanket rule applied mechanically, not a verse-by-verse decision.

**What the references say.**

- Wickes (*Poetical Books*, p. 34), whom the OSHB cantillation page names as the basis for these divisions, does say that Azla Legarmeh stands in for Oleh veYored on the first word of a verse. But he lists where: the titles לְדָוִד (Pss 26, 27, 35, 37, 103, 138, 144) and לִשְׁלֹמֹה (Ps 72), and opening Hallelujahs. Psalm 93:4 is not on that list. (Caveat: this was read from the archive.org scan, whose OCR is poor, and not in full.)
- Price (*The Syntax of Masoretic Accents in the Hebrew Bible*, ch. 13–14) says the Ole-WeYored segment "has no substitute segment", and cites Ps 93:4 by name among the Great Rebia clauses that have a preceding Legarmeh. That is the reading this PR gives.
- Within the data, Ps 93:3 (נָשְׂא֤וּ נְהָר֨וֹת ׀ יְֽהוָ֗ה) is already coded `1.0.0, 1.0, 1, 0`, the same shape this PR gives verse 4. Miqra according to the Masorah also keeps מִקֹּלוֹת ׀ מַיִם רַבִּים together on one poetic line.

**Your question about the XML.** Nothing in this repository generates the `n` values, and the structure viewer reads `wlc/*.xml` directly, so editing the XML is the right way to make this fix.

**Follow-up, not blocking.** Thirteen other verses carry the same `2` on a first-word Azla Legarmeh and are outside Wickes's list: Ps 32:8, 36:7, 38:12, 76:6, 81:11, 87:5, 91:4, 91:15, 93:5, 113:9, and Prov 6:14, 6:22, 30:15. Each needs its own look. In the other direction, most of the opening Hallelujahs that Wickes does list (Pss 111–113, 135, 148–150) are coded as ordinary breaks, because the WLC writes הַלְלוּ יָהּ as two words there.

**Outcome:** we intend to merge this. The website serves the `gh-pages` branch, so the structure viewer will show the change only after the site is next updated; that is being planned separately.

I've been experimenting with the MapM text today to see if I can help with https://github.com/Noleli/trop-analysis/issues/10.  The code in that repository happens to include a consistency check for whether the cantillation marks it finds include any instances of tsinnorit.  After handling the fact that MapM uses tsinnorit (a.k.a. Unicode "zarqa") for the accented syllable of milra words where there's a postpositive zarka (a.k.a. Unicode "zinor"), this still had one hit on Exodus 36:2:

> וַיִּקְרָ֣א מֹשֶׁ֗ה אֶל־בְּצַלְאֵל֘

This surely isn't a real tsinnorit, so the only reason I can think of why it would be present would be so that the cantillation mark doesn't collide with the head of the lamed, even though that seems as though it should just be a rendering consideration.  But the [rendered text of this verse on WikiSource](https://he.wikisource.org/wiki/%D7%A9%D7%9E%D7%95%D7%AA_%D7%9C%D7%95/%D7%98%D7%A2%D7%9E%D7%99%D7%9D) has a normal postpositive zarka instead:

> וַיִּקְרָ֣א מֹשֶׁ֗ה אֶל־בְּצַלְאֵל֮

The MapM spreadsheet does show [variants for Exodus 36:2](https://docs.google.com/spreadsheets/d/1mkQyj6by1AtBUabpbaxaZq9Z2X3pX8ZpwG91ZCSOEYs/edit?gid=957434826#gid=957434826&range=E2736), but they're between אֶל־בְּצַלְאֵל֮ (with postpositive zarqa) and אֶל־בְּצַלְאֵ֘ל (with tsinnorit on the alef).  The documentation note refers to another note on [Exodus 30:11](https://docs.google.com/spreadsheets/d/1mkQyj6by1AtBUabpbaxaZq9Z2X3pX8ZpwG91ZCSOEYs/edit?gid=957434826#gid=957434826&range=E2550).  As far as I understand that note, it says that there is an irregular manuscript form here where the zarka appears to be before the lamed and not after it, but they observe that this is only because the head of the lamed means that the zarka cannot extend to the left, and that there is "no place" to copy this irregular form to the digital edition.

I notice that Exodus 30:11 in `MAPM.xml` here has a zarka as I'd expect, so I think the accentuation of Exodus 36:2 may be a mistake in the edition found here (perhaps just due to using an older version of the MapM text).  Does this make sense to you?  Thanks!

I reproduced this at `3d15126fb1ef74867fc1434be1942e837932691f`: in `MAPM/MAPM.xml`, Exodus 36:2 has U+0598 after the final lamed in Bezalel. The [Wikisource MAM text](https://he.wikisource.org/wiki/שמות_לו/טעמים) linked in the report displays U+05AE there. Ben Denckla's encoding documentation explains the distinction between stress zarqa and postpositive zarqa and identifies Exodus 36:2 in its discussion of lamed-related displacement:
[The encoding of MAM for Sefaria](https://bdenckla.github.io/MAM-basics/MAM-for-Sefaria/index.html)

A narrow source-alignment candidate replaces only that terminal U+0598 with U+05AE. I verified that it changes exactly one Unicode code point, preserves every consonant and all remaining file content, and leaves valid XML. This is not a global replacement rule: U+0598 has legitimate uses elsewhere. The README already cautions that the MAPM files may be outdated, which supports considering source-version drift without proving the history of this particular character.

One clarification to the report: Exodus 30:11 in this pinned MAPM file has neither U+0598 nor U+05AE, so it cannot serve as the stated positive comparison. That reference may need correction; I have not guessed a replacement verse.

This candidate updates the stored MAPM encoding toward the cited source edition; it does not alter WLC or certify manuscript readings.
