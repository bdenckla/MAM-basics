## Why

`MAPM/MAPM.xml` is David Troidl's OSIS conversion of Miqra according to the Masorah (MAM), finished in February 2014. MAM has been corrected a great deal since: the text differs from today's MAM in 2,260 of the 23,210 verses the two share. One of those differences is the subject of openscriptures/morphhb#109 (the zarqa in Exodus 36:2), which this pull request resolves.

## What changes

- **`MAPM/MAPM.xml`** is replaced by today's MAM, generated by [MAM-basics](https://github.com/bdenckla/MAM-basics) at commit [83caf168](https://github.com/bdenckla/MAM-basics/commit/83caf1689a7c8e382254af07ecb5373819ce3f07) (its `MAM-morphhb/MAPM.xml`, byte for byte).
- **`MAPM/readme.txt`** gives the date, the MAM-basics commit, what differs from the 2014 file, and the license with MAM's attribution statement.
- **`README.md`**: the MAPM paragraph's last line, "The MapM has since progressed, so our files may not be up to date", now says when the file was regenerated and where a newer version may be.

## The form is the 2014 file's, with five deliberate changes

The new file keeps the 2014 file's OSIS form and line layout: the book groups and their Hebrew titles, the 54 parashot and Psalms' five books as titled sections, chapter and verse milestones with Hebrew numbers, `<p>` and `<lb/>` for the breaks, `<lg>` and `<l level>` for the poetic lines of Psalms, Proverbs and Job 3:2–42:6, and the `x-paseq`, `x-big`, `x-small`, `x-suspended` and `x-reversednun` segs. It still validates against the OSIS 2.1.1 schema. What differs:

1. **Verse numbering is BHS's throughout**, as in WLC and in this repository's `wlc/`. The 2014 file used MAM's own numbering in four places and BHS's in the Decalogues. Eight English `type="variant"` notes now say where MAM's own numbering differs. Joshua 21:36–37, which MAM's text does not have, are left out.
2. **Each qere is marked**: `<seg type="x-ketiv">…</seg> <seg type="x-qere">…</seg>`, in MAM's order, so 133 of the 1,047 pairs have the qere first. The 2014 file wrote the qere as plain text after the ketiv, which a program could not always find. A ketiv without a qere and a qere without a ketiv are `x-ketiv-velo-qere` and `x-qere-velo-ketiv` segs.
3. **No song tables.** The eight songs that the 2014 file set as tables (Exodus 15, Deuteronomy 32 and six more) are ordinary verse lines, with each gap in the song an `x-space` seg.
4. **Well-formed good endings.** The good endings of Isaiah, Malachi, Ecclesiastes and Lamentations are `x-good-ending` segs inside each book's last verse; the 2014 file had two of the four, as extra verses that were never closed.
5. **New notes and segs from MAM:** notes on scroll differences, on words with large, small or hung letters, and on silluq before meteg; an `x-implicit-maqaf` seg; all nine inverted nuns (the 2014 file lacked Psalms 107's seven). The 2014 file's `x-symbol` segs (♫, ↓↑), links on MAM's Wikisource page rather than text, are gone.

## License

MAM is available under CC BY-SA 4.0, with attribution to Hebrew Wikisource; `MAPM/readme.txt` gives MAM's statement in full. The 2014 file was released under CC BY-SA 3.0 Unported.

## One known reader

OpenScriptorium's `oshb_features_importer.rb` downloads this file from master, unless it has a cached copy, and reads it line by line. The new file keeps the 2014 line layout so that the importer goes on working, but the importer as it stands would misread the marked qere: it would take `<seg` as the qere of every ketiv-first pair. A small patch to the importer that reads the marked qere is drafted; if this pull request is accepted, the patch will be offered to OpenScriptorium. Nothing in this repository reads `MAPM/`.

## The web site

hb.openscriptures.org serves the `gh-pages` branch, last merged from master on 2022-02-08, so the site shows this change only after master is merged into `gh-pages` again.

## How it was checked

The file validates against the OSIS 2.1.1 schema. Compared verse by verse with MAM-basics' other OSIS export, MAM-OSIS, its text differs only by a stray space that MAM-OSIS has before the sof pasuq of Deuteronomy 6:4. In Exodus 36:2, where the 2014 file has HEBREW ACCENT ZARQA (U+0598), the new file has HEBREW ACCENT ZINOR (U+05AE), as MAM does. An element count against the 2014 file matches on every kept feature: 39 books, 9 book groups, 59 sections, 101 titles, 1,858 chapter milestones and 9,756 poetic lines.

## Why

This project has no automated checks, so every pull request has had to be verified by hand. With few people able to review, that is slow, and it is how #108 came to wait eighteen months. This adds a small set of checks that run on every pull request and on pushes to `master`.

## What it checks

Any of these failing fails the run:

- every tracked XML file is well-formed;
- `wlc/` has 39 books and 23,213 verses, and every word has a lemma, a morph code and a unique five-character id;
- `MAPM/MAPM.xml` has balanced verse markers and the same verse inventory as `wlc/`, apart from Josh 21:36–37, which MAM's text does not have;
- no operating-system junk files (`Thumbs.db`, `.DS_Store`, `desktop.ini`) are tracked.

## What it reports

On a pull request it also writes a **data change summary** to the job summary: which words in `wlc/` changed and in which field (text, lemma, morph, `n`), any word ids added or removed, and how many `MAPM/` verses changed. The summary never fails the run; it is there so a reviewer can see at a glance what a change touches. For #108 it would have been one row:

| verse | id | field | before | after |
|---|---|---|---|---|
| Ps.93.4 | `19AHF` | n | 2 | 1.0.0 |

## Also in this pull request

The four `Thumbs.db` files are removed and such files are ignored from now on, as osjc proposed in #111. Without that the new junk-file check would fail on `master`.

## How it was tested

Run locally with the same script:

- on `master` before #108, #110 and #114 were merged: fails, on the 2014 `MAPM.xml` (unclosed verses, text outside verses, different verse numbering) and the `Thumbs.db` files;
- on this branch: passes (`wlc/: 23213 verses, 306785 words`, `MAPM/: 23211 verses`) in about four seconds.

This pull request is the first real run of the workflow on GitHub.

## Notes

- The script (`.github/scripts/validate_data.py`) uses only the Python standard library, so it can be run locally with `python3 .github/scripts/validate_data.py`, or with `--base <checkout of master>` to see the change summary.
- The workflow uses the `pull_request` trigger with `contents: read` only, so pull requests from forks get a read-only token and no secrets.
- It does not validate `wlc/` against the OSIS schema, because the word `id` attribute is not in that schema and the files do not pass it today. Morph codes are checked for shape, not against the full code tables; that would be a good later addition.
